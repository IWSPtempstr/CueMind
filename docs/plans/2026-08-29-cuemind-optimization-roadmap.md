## P0 询问完成延迟（大幅缓解，残留待产品裁决）

**问题**：A 阶段验收不通过项——完成 P95=11.47s（4B）> 决策 67 预算 7s；基线切 8B 后未复测。

**处置（先测后判）**：新增 [scripts/measure-ask-latency.ts](../../scripts/measure-ask-latency.ts)（冻结题集 8 题、串行、真实搜索、预热去 dev 冷启动污染、首事件/答案首字节/完成三口径）。实测 8B 基线完成 P95=13032ms，stages 分解 `kw≈1.1s / search≈2.2s / gen≈4.8s` → 生成段主导。

**修复（预案①：收紧输出长度，三轮迭代）**：ASK_PROMPT 增加「答案 ≤80 字、引用来源 ≤2 条」；`ASK_MAX_TOKENS` 1024→512。

**复测轨迹**：13032 → 8008 → 7032 → 7441 → **7119ms**；首事件（searching，A/B 口径首字节）P95=1733ms ✅；schema 违规 0（无截断回退）。

**结论（不虚标）**：缺陷**未完全关闭**——三轮修复后完成 P95 稳定在 7.0–7.4s 区间（预算线 ±6% 内），较修复前 -45%；剩余差距由 8B 模型在 4060 Ti 上的解码吞吐主导（引用 JSON ~300 tokens/题 × ~50 tok/s ≈ 3.3s 生成段下限，叠加搜索 ~1.8s）。计划内修复手段已用尽（①输出长度×3 轮；②让位队列在串行测量不适用）。

**待裁决项**（进一步压缩需产品取舍，不静默实施）：
- 接受现状并修订决策 67 预算口径（如完成 ≤7.5s）——须决策文档留痕；
- 或继续压缩答案质量（更短答案/单引用），牺牲引用式回答的产品承诺；
- 或硬件/推理手段：投机解码、量化档位、更强 GPU。

**其余遗留**：
- n=8 样本下 P95 对最差单题敏感；任何模型/提示词/硬件变更后须复跑该脚本。
- 「答案首字节」在服务端缓冲校验设计下 ≈ 完成时间；决策 67「首字节 ≤3s」按首事件口径达标（1.7s）。若产品要求答案内容级首字节 ≤3s，需增量校验架构改造（与 fail-closed 权衡），另立决策。

## P1 降级回答过滤（已完成）

**问题**：「没找到可靠来源…」「回答生成失败：…」进入总结 `<meeting_asks>`、vault「会中询问」小节、训练信号匹配。

**方案**：[lib/ask-history.ts](../../lib/ask-history.ts) `extractAskExchanges` 跳过 `isDegraded` 标志与降级文案前缀（`DEGRADED_ANSWER_PREFIXES`）——双路径覆盖内存态与 DB 回读（无标志）态。

**验收**：`test-summarize-route.ts` 用例 e；既有 a–d 全绿。

**遗留**：DB 侧 `chat_messages` 无终态列，前缀启发式是过渡方案 → 根治归 P2。

## P2 询问持久化完整性（待排期）

**问题**：`chat_messages` 只存 role/content；sources、提取关键词、终态（answered/degraded/invalid_schema/model_failed）全丢。后果：刷新后 vault「会中询问」来源链接缺失；训练信号以问题原文代理提取词；决策 65「带终态标签的真实决策轨迹」在询问侧无终态。

**方案要点**：
- `lib/chat-store.ts`：表增列 `sources_json`、`keywords_json`、`final_state`（TEXT，可空）。新库 `CREATE TABLE IF NOT EXISTS` 直接带新列；旧库启动时 `PRAGMA table_info(chat_messages)` 检测缺列 → `ALTER TABLE ADD COLUMN`（只加列、不迁移历史数据）。
- `app/page.tsx` `toStoredAskMessages`：透传 sources/keywords/finalState；`/api/chat-messages` 路由同步解析。
- `scripts/export-training-data.ts`：`readChatMessageRows` 增读 `keywords_json`，信号匹配改用真实提取词（替代问题原文代理）。
- `app/replay/page.tsx`：拉取询问历史渲染（含来源链接与降级标识）。

**验收**：刷新后 sources/终态可恢复；replay 断言；训练导出用真实提取词命中；旧库升级幂等（重复启动不重复 ALTER）。

**依赖**：无前置；P3 的提取词命中依赖本项。

## P3 训练信号严谨化（待排期）

**问题**：① 命中无时序约束——出卡前的提问也计入「出卡后仍被问」；② 同一候选双通道（--useful + 询问命中）重复造 DPO 对；③ 子串命中过宽（term 长度 <2 亦匹配）。

**方案要点**：
- `readChatMessageRows` 增读 `created_at`；命中判定要求**问题时间 ≥ 候选 `created_at`**（card_shown 统计与 model_skip 命中同规则）。
- 双通道去重：同候选已在 `--useful` 通道造对时，询问命中不重复造对（统计口径：报告分别计数、DPO 行不重复）。
- `questionMentionsTerm`：term trim 后 <2 字符不匹配。

**验收**：`test-export-training-data.ts` 增时序反例（出卡前提问不计入）、去重断言、短 term 断言；既有全绿。

## P4 用户裁决与失败可见（待排期）

**问题**：① 决策 65「人工把关」被自动信号通道绕过——系统能发现漏报、用户无法确认漏报；② 询问降级率/来源不足率只在服务端日志，用户侧不可见。

**方案要点**：
- 卡片侧「该词应出卡」漏报裁决入口（对齐决策 6 的「有用」标记模式）：用户确认写入裁决存储，训练导出只认**已确认**的漏报（自动命中降为候选提示，不直接进 DPO）。
- 设置健康区增「询问失败模式」：降级率、来源不足率、近 20 次完成延迟（本地内存统计，无外发）。

**验收**：裁决入口端到端（确认 → 导出认）；健康区字段断言；决策文档补「人工确认后才进训练」红线表述。

**依赖**：P2 的终态列（失败模式统计的数据源）。

## P5 工程卫生（待排期）
